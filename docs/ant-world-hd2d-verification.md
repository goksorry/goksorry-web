# HD-2D 월드 구현·검증

2026-11-15 KST. 홈과 연결된 정보·기록 흐름 구현. 커밋·푸시·웹 배포는 수행하지 않았다. 운영 DB에는 기존 기록 마이그레이션을 적용했다.

## 구현

- Three.js 사선 3D 골목, 픽셀 재질, 4방향 캐릭터 atlas, 벽면 프레임과 투영 좌표를 공유하는 HTML 지수·피드 화면. 아트 원본·프롬프트·재생성 절차는 [아트 기록](ant-world-hd2d-art.md).
- 공통 상세 레이어의 지수·피드 탭, 종목·커뮤니티 선택, 전체 복귀, Escape·배경·닫기와 포커스 복귀. 기존 필터·더 보기·원문·예쁜말·테마·인증 접근 유지. 모바일은 별도 카메라와 목록, 스크롤 중 유지되는 지수·피드 바로가기, 하나의 하단 시트.
- 광장·생태계·전장·방송·극장에 같은 에셋·장면 생성기 사용. 장애물 우회 이동, 가까운 입구 동작. 첫 방문 설정은 메뉴 안으로 이동. 쿠키 안내는 홈 문서 흐름에 배치. 상세·메뉴를 열면 배너는 잠시 숨겨서 페이지 하단에서도 레이어를 가리지 않는다.
- 군중 비율은 전체 희망·공포·중립 건수에서 계산. 대표 근거 배열은 글 표시에만 사용. 희망·공포 비율은 중립 제외, 지수는 기존 보정 산식. 빈 표본·중립·소표본·최초 로딩·조회 실패·갱신 지연 구분, 실패 시 마지막 정상 데이터·시각 보존.
- 극장 그래프 0·5·10 축척, 누락 구간 분리, 날짜 전환, 저장 시점 근거, 동일 HD-2D 렌더러를 이용한 PNG. 상세를 읽는 동안 재생 일시 정지. `WorldFrame v1`, 공개 API 계약·기존 링크 유지. 추가 LLM 호출 없음.

월드 검사는 공포 우세·희망 우세·중립만 존재·소표본·빈 표본, 최초 조회·503·갱신 지연·마지막 정상 데이터, 에셋 실패·동작 줄이기, 숨김 탭의 실제 렌더·폴링 중단을 포함한다. 데스크톱 1440×1000과 모바일 390×844에서 48/24개 개미로 검사했다. 모바일 종목명 14px 이상, 주요 동작 44px 이상, 가로 넘침, 키보드 탭 전환·Home/End·Escape·포커스 복귀를 확인했다. 전체 검사 이후 모바일 sticky의 body 스크롤 컨테이너를 수정했으며, 양 브라우저 후속 4개 검사와 최종 최적화 빌드의 실제 데이터 화면에서 스크롤 위치·상세 열기·포커스 복귀를 재확인했다.

Firefox 기본 헤드리스 환경은 WebGL 생성에 실패했다. 정적 대체 기능은 동작했으며 렌더 검사 5개는 실패했다. 동일 브라우저를 `xvfb-run -a ... --headed`로 실행해 전체 31개를 통과했다. 애플리케이션의 WebGL 오류를 무시하거나 검사에서 제외하지 않았다.

로그인 헤더의 클라이언트 모의 API 검사는 최적화 서버의 초기 서버 세션 주입 때문에 모의 응답을 사용하지 않아 실패했다. 기존 검증 방식대로 개발 서버에서 통과했다. 실제 Google OAuth 왕복·계정 생성은 이번 증거에 포함하지 않는다.

## 렌더 성능

최적화 빌드에서 시나리오별 2.5초. `renderer.render()` 실행 횟수, 호출 간격, CPU 호출 시간을 각각 기록했다. rAF 간격도 별도 기록한다.

| 브라우저·viewport | 이동 / 상세 / 재생 렌더 fps | 렌더 간격 p95 | CPU 호출 p95 |
| --- | --- | --- | --- |
| Chromium 1440×1000, 48개 | 60.00 / 59.98 / 60.31 | 16.7ms | 0.4–0.5ms |
| Chromium 390×844, 24개 | 30.00 / 29.99 / 30.00 | 33.4ms | 0.4–0.6ms |
| Firefox 1440×1000, 48개 | 59.23 / 59.24 / 58.78 | 17.12ms | 1–2ms |
| Firefox 390×844, 24개 | 29.53 / 29.60 / 29.59 | 34.36–34.50ms | 1ms |

Chromium은 SwiftShader, Firefox는 llvmpipe 소프트웨어 렌더러다. GPU timer extension이 없어 GPU 완료 시간은 `null`이며, CPU 시간과 구분한다. 위 수치는 실제 렌더 제출 빈도이며 화면에 표시된 프레임 완료 시각을 측정한 값이 아니다. 60/30fps 목표에 근접한 로컬 결과다. **물리 모바일 기기·하드웨어 GPU·Lighthouse·운영 배포 성능은 미검증**이다.

원자료: [Chromium](verification/hd2d/chromium-production-performance.json), [Firefox](verification/hd2d/firefox-production-performance.json). 개발 서버 측정은 같은 폴더의 `*-dev-performance.json`으로 분리했다.

## 운영 기록 복구

대상: 연결 프로젝트 `oldbntwoxhtaehpirepn`.

1. `supabase db push --dry-run`에서 `20261114171745_world_snapshots.sql` 한 건만 확인했다.
2. 기존에 커밋된 마이그레이션을 CLI로 적용했다. SQL 파일을 새로 만들거나 수동 데이터 행을 삽입하지 않았다. 후속 dry-run은 `Remote database is up to date.`였다.
3. 다음 정상 수집 후 첫 저장은 **2026-11-15 11:50:32.537 KST**, 버킷 11:50, 표본 434건이었다. 수집 `last_run_at`과 별도의 `captured_at`을 확인했다. RLS 활성, anon SELECT 거부, authenticated INSERT 거부, service_role INSERT 허용을 확인했다.
4. PostgREST의 `+00:00`와 생성 슬롯의 `.000Z`를 문자열로 비교하던 버그를 발견했다. `Date.parse`로 같은 시점을 매칭하도록 수정하고 회귀 검사를 추가했다.
5. **12:33 KST** 운영 DB 읽기 검증에서 수정된 로컬 최적화 서버는 144개 슬롯 중 **실제 5개 기록**(11:50–12:30)을 반환했다. 공백은 그대로 유지했다. 현재 월드 API는 운영 응답과 동일한 표본 422건, 데이터 기준 12:30:19.719 KST, 희망 약 37.2%·공포 약 62.8%였다.
6. 같은 시각 운영 `goksorry.com` 재생 API는 HTTP 200이지만 구버전 문자열 매칭으로 기록 0개였다. **웹 수정 배포 후 운영 재생 API 확인이 릴리스의 남은 조건**이다. DB 적용·수집·저장 성공이 웹 수정 배포를 뜻하지 않는다.

근거: [운영/로컬 API 대조](verification/hd2d/live-recording-api.json), [실제 데이터 브라우저](verification/hd2d/live-data-browser.json). 로컬 모의 서버와 운영 DB 검증 서버를 같은 `.next` 데이터 캐시로 동시에 검증하면 모의 집계가 재사용될 수 있다. 최종 운영 DB 증거는 모의 서버를 종료하고 `.next/cache/fetch-cache`를 비운 뒤 새 프로세스에서 수집했다. 자격증명은 런타임 프로세스에만 전달했으며 파일·산출물에 저장하지 않았다.

## 재현

- 독립 개발 검사: `npm run test:world -- --project chromium`. Firefox 렌더 검사는 이 호스트에서 `xvfb-run -a npm run test:world -- --project firefox --headed`.
- 이미 준비한 격리 서버(3100, 모의 PostgREST 3101)를 사용할 때만 `WORLD_TEST_REUSE_SERVER=1`을 지정한다. 최적화 검사는 `.env.example`로 빌드한 후 `playwright.world.config.ts`에 지정된 **로컬 모의 환경 변수**로 `next start`를 실행한다.
- 운영 DB 검증 전에는 모의 서버를 종료하고 로컬 Next 데이터 캐시를 제거한다. 동일 빌드 디렉터리에서 개발 서버와 최적화 서버를 동시에 실행하지 않는다.
- 원본 아트 재캡처는 `WORLD_CAPTURE_ART=1`과 `tests/world-hd2d.spec.ts`를 사용한다. 상태별 수치·실제 근거는 HTML에 남기며 정적 PNG에 굽지 않는다.
